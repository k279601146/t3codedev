# T3 Code 成熟化滚动开发进度

更新日期：2026-06-30

## 长期目标

将 T3 Code 持续推进为成熟的商业化 AI 编程助手 IDE 客户端。方向上参考 Codex、Claude Code 等成熟同类产品，但不做简单外壳复制；优先围绕 T3 Code 自身的桌面端、本地 server、provider 编排、商业账号、模型网关、用量计费、沙箱、插件/技能和可观测性体系推进。

## 调研依据

- [OpenAI Codex 官方手册](https://developers.openai.com/codex/codex-manual.md)：关注 Codex app、CLI、IDE、云端、automations、skills、plugins、MCP、hooks、permissions、app-server、in-app browser、computer use、worktrees、security/governance 等成熟能力面。
- [OpenAI Codex CLI 文档](https://developers.openai.com/codex/cli/)：关注模型配置、CLI/IDE 入口和本地 agent 运行形态。
- [Anthropic Claude Code 官方文档](https://docs.anthropic.com/en/docs/claude-code/overview)：关注终端原生 agent 工作流、配置、slash commands、hooks、MCP、权限、子代理和团队治理能力。
- [Anthropic Claude Code 权限文档](https://code.claude.com/docs/en/permissions)：关注 allow/ask/deny 权限规则、`/permissions` 管理入口、持久与会话授权边界。
- 本仓库现状：`apps/server` 已具备 provider/orchestration/checkpoint/git/observability 基础；`apps/web` 已具备 IDE 三栏、模型选择、技能、插件、自动化、Diff、终端等体验；`apps/desktop` 已具备商业登录、内置引擎、IPC、安全存储、更新和遥测雏形；`packages/shared` 已有商业引擎、用量、观测、工作区配置等共享能力。

## 成熟化方向

### 功能成熟

- 多 provider、多模型和模型路由体验稳定：Codex、Claude、OpenCode、Cursor/ACP 与 sub2api 网关模型列表一致。
- Agent 能力平台化：skills、plugins、MCP、browser/computer use、automations、hooks、worktrees、review 能力形成统一入口和状态反馈。
- IDE 工作流闭环：项目、会话、Diff、编辑器、终端、source control、checkpoint 和 PR 流程稳定衔接。

### 商业成熟

- 客户端只持有 IDE JWT；真实模型密钥只在 sub2api 或上游服务端保存。
- 登录、套餐、用量、限额、升级和账单入口在客户端可感知，但扣量和权限判断由服务端完成。
- 内置 `ai-engine`、沙箱、自动更新、崩溃恢复和版本回滚具备可发布产品的安全边界。

### 性能成熟

- Provider 状态、模型目录、用量查询和前端渲染避免重复慢请求。
- 关键链路观测覆盖 TTFT、provider turn、RPC、orchestration、git、terminal、desktop APM 和引擎崩溃。
- 对长上下文、大文件、多事件流和高频 UI 更新建立背压、批处理或缓存策略。

## 阶段 1：模型目录解析收敛

### 阶段目标

先处理一个会影响商业化模型路由体验的基础问题：服务端 Provider 状态和桌面 IPC 都会读取 sub2api/OpenAI 兼容 `/models`，但解析逻辑分散，字段兼容性不一致。将解析逻辑收敛到 `packages/shared`，让后续模型列表、模型选择器和套餐过滤有统一输入。

### 已完成项

- 新增 `packages/shared/src/commercialEngineModels.ts`，统一解析网关 `/models` 响应。
- 支持 OpenAI 兼容字段 `id`、`name`、`owned_by`，同时兼容 sub2api 可能返回的 `display_name`、`provider`。
- 对模型 ID 做 trim、去空、去重；名称为空时回退到模型 ID；provider 缺失时回退为 `unknown`。
- 新增 `@t3tools/shared/commercialEngineModels` 显式 subpath export，符合 shared 包不新增总入口 barrel 的约束。
- 桌面端 `apps/desktop/src/ipc/methods/gatewayModels.ts` 改为复用共享解析逻辑。
- 服务端 `apps/server/src/provider/Layers/CodexProvider.ts` 改为复用共享解析逻辑，避免服务端只识别 `display_name` 导致模型名称退化为 slug。
- 新增 `packages/shared/src/commercialEngineModels.test.ts` 覆盖 OpenAI 兼容字段、sub2api display 字段、去重、回退和非法结构。

### 当前状态

- 阶段 1 代码修改已完成。
- 按本仓库测试约束，本阶段不运行依赖下载、编译、dev server 或完整测试，仅做轻量源码检查与 `git diff --check`。
- 该改动不会改变网关请求地址、鉴权方式或扣量逻辑，只统一解析模型目录响应。

### 下一阶段计划

1. 性能方向：为商业模型目录和商业用量查询补齐缓存/失效策略，避免 Provider 状态刷新频繁打到网关。
2. 商业方向：梳理登录态、模型可用性、用量限制和升级入口之间的 UI 状态，避免“能选但不能用”或“用量已限但提示不清”的体验。
3. 功能方向：将网关模型 provider/name 元信息进一步传入模型选择排序和分组，使多模型体验更接近成熟 IDE 产品。

### 遗留问题

- 当前模型能力仍由 Codex 商业模型统一能力描述兜底，尚未按模型 family 精细区分上下文窗口、推理档位、图像能力和价格等级。
- 网关 `/models` 的真实字段结构需要继续以 `D:\workspace\sub2api-fork` 和线上响应为准做兼容验证。
- 本阶段只新增测试文件，未运行 Vitest；后续在允许轻量单测时可优先运行 `packages/shared/src/commercialEngineModels.test.ts`。

## 阶段 2：商业模型目录/用量查询缓存

### 阶段目标

降低商业模型目录、账户余额和用量查询对网关的重复压力，减少 provider 状态刷新、桌面模型列表读取和侧边栏用量轮询带来的延迟抖动。缓存必须按 gateway URL 和 IDE JWT 指纹隔离，避免不同账号或不同网关之间复用商业数据。

### 已完成项

- 新增 `packages/shared/src/ttlMemoryCache.ts`，提供纯内存短 TTL 缓存工具，供 server/desktop 复用，避免重复实现 Map 过期和容量裁剪逻辑。
- 新增 `packages/shared/src/ttlMemoryCache.test.ts`，覆盖 TTL 过期和容量淘汰行为。
- 服务端 `apps/server/src/provider/Layers/CodexProvider.ts` 为商业模型目录、账户余额和用量查询增加缓存：
  - 模型目录缓存 5 分钟。
  - 余额和用量缓存 15 秒。
  - 缓存 key 使用请求类型、URL 和 JWT SHA-256 指纹，不保存明文 JWT 到 key。
  - 仅缓存成功结果；网络失败、HTTP 非成功和解码失败仍走原有 warning 降级路径。
- 桌面端 `apps/desktop/src/ipc/methods/gatewayModels.ts` 为模型列表和商业用量 IPC 增加同类缓存：
  - 模型列表缓存 5 分钟。
  - 用量快照缓存 15 秒，覆盖侧边栏 10 秒轮询场景。
- 保留服务端和桌面端各自的鉴权、请求地址和错误降级逻辑，缓存只包裹读取结果，不参与扣量或权限判断。

### 当前状态

- 阶段 2 代码修改已完成。
- 缓存边界为进程内短 TTL，重启即清空；不会写入磁盘，也不会改变 sub2api 服务端的计费权威性。
- 按本仓库测试约束，本阶段不运行编译、dev server 或完整测试，仅做轻量源码检查与 `git diff --check`。

### 下一阶段计划

1. 商业方向：梳理“用量已限、余额不足、未登录、套餐不可用、模型不可用”在 composer、模型选择器和设置菜单中的提示闭环。
2. 功能方向：把网关模型 provider/name 元信息继续传入模型排序和分组，减少用户在多模型列表里的识别成本。
3. 性能方向：基于已有 `t3_provider_first_assistant_delta_latency` 和 desktop APM 事件，梳理可展示的 TTFT/错误率入口。

### 遗留问题

- 当前缓存没有跨进程共享；如果 desktop 和 server 同时查询同一网关，仍会各自保留一份短 TTL 缓存。
- 当前没有请求合并机制；同一 key 在同一瞬间并发 miss 时仍可能发起多次请求，后续只有在实际观测到并发压力时再引入合并，避免过早复杂化。
- 缓存 TTL 是本地常量，后续可根据网关返回的 `Cache-Control` 或自有配置动态调整。

## 阶段 3：用量限制与升级提示闭环

### 阶段目标

### 已完成项

- 当前窗口耗尽时显示“当前 5 小时额度已用完”，每周窗口耗尽时显示“每周额度已用完”，并保留原 `formatUsageLimitResetHint` 兼容 API。

- `apps/web/src/components/ChatView.tsx` 在用量门禁 toast 中加入“升级套餐”和“查看账单”两个动作，并使用商业账号站点配置生成目标链接。
- 修正 `apps/web/src/components/ui/toast.tsx` 主操作按钮没有透传 `onClick` 等 `actionProps` 的根因，已有 `Retry`、`Settings`、`Update` 类 toast 主操作也能正确执行。
- 新增 `apps/web/src/lib/commercialAccountLinks.test.ts` 和补充 `apps/web/src/lib/commercialUsageGate.test.ts`，覆盖账号链接回退、当前/每周限额文案与操作路径。

## 阶段 5：Provider/TTFT 性能观测看板

### 阶段目标

把性能优化从“感觉慢”推进到“能在本地诊断页看到事实”：复用已有 `server.getTraceDiagnostics` RPC 和本地 trace 文件，在设置页 Diagnostics 中展示 provider 发送/转向回合的耗时、失败次数和 TTFT 摘要。该阶段不新增遥测链路，不采集 prompt、代码内容或密钥，只从现有 span attributes 和日志事件聚合低敏 metadata。

### 已完成项

- 扩展 `packages/contracts/src/server.ts` 的 `ServerTraceDiagnosticsResult`，新增 `providerPerformance` 结构化结果。
- `providerPerformance` 覆盖 provider、回合数、失败数、平均/最大回合耗时、TTFT 样本数、平均/最大 TTFT 和最后出现时间。
- `apps/server/src/diagnostics/TraceDiagnostics.ts` 复用现有 trace 聚合流程：
  - 识别 `provider.operation=send-turn|steer-turn` 或 `ProviderService.sendTurn/steerTurn` span。
  - 从 `provider.kind`、`provider`、`provider.name` 读取 provider 名称。
  - 从 `provider first assistant delta observed` 日志事件读取 TTFT 样本。
  - 按 provider 聚合并按最近出现时间排序，保留 Top 结果。
- 对只有 TTFT 日志但没有可识别 provider turn span 的情况，回合耗时保持为空，避免把缺失样本误展示为 `0ms`。
- `apps/web/src/components/settings/DiagnosticsSettings.tsx` 在 Diagnostics Trace 区域新增 “Provider 性能” 表格，展示 provider、回合数、失败数、平均/最慢回合、平均/最慢 TTFT 和最后出现时间。
- 补齐现有测试/浏览器测试 mock 中的 `providerPerformance` 字段，保持 contracts 扩展后的调用形状一致。
- 新增 `apps/server/src/diagnostics/TraceDiagnostics.test.ts` 聚合测试入口，覆盖 provider turn + TTFT 聚合，以及 TTFT-only 时长不造假的场景。

### 当前状态

- 阶段 5 代码修改已完成。
- 数据源仍是本地 trace 文件和既有 RPC，不改变 OTLP、metrics 或远端上报行为。
- 展示的是 provider turn 发送/转向请求耗时和首次 assistant delta 延迟，适合定位“请求发起慢、provider 失败、首字慢”等问题；它不是完整生成耗时统计。
- 按本仓库测试约束，本阶段不运行 Vitest、编译、dev server 或浏览器截图，仅做轻量源码检查与 `git diff --check`。

### 下一阶段计划

1. 发布质量方向：梳理桌面端内置 `ai-engine`、server 子进程、自动更新和崩溃恢复状态，把用户可感知的失败路径收敛到一个诊断/恢复入口。
2. 性能方向：继续补齐 provider 全链路耗时样本，后续如果 trace 中出现完整 runtime turn 结束事件，再把完整生成耗时纳入同一诊断视图。
3. 商业方向：将模型能力标签和用量状态结合，在额度紧张时优先提示省额度模型或升级入口。

### 遗留问题

- TTFT 依赖 `provider first assistant delta observed` 日志事件；如果运行时没有产生 assistant delta，当前不会有 TTFT 样本。

## 阶段 22：自动化权限审计本地服务持久化最小实现

### 阶段目标

阶段 21 已经把自动化权限审计事件提升为 contracts 协议，但事件仍停留在浏览器 `localStorage`。成熟的商业 IDE 不能只依赖单个浏览器 profile 保存高风险权限动作记录。本阶段先实现本地 server 侧最小持久化：通过 WebSocket RPC 接收前端审计事件，写入本地 SQLite，并提供按来源、结果、时间、关键词和 cursor 的查询入口，为后续 UI 回填、团队审计和 SaaS 聚合打基础。

### 阶段作用

- 把自动化权限审计从“浏览器本地记录”推进为“server 可查询日志”，让审计链路开始具备跨页面、跨刷新和本地服务级恢复能力。
- 为 `AutomationPermissionPolicyActionAuditIngestInput` 和 `ListInput` 提供真实 server 实现，验证阶段 21 的协议边界不是空草案。
- 使用项目既有 SQLite migration、Effect Service/Layer 和 WS RPC 模式，不新增另一套持久化架构。
- 采用事件 ID 幂等写入，前端重复补同步不会制造重复审计记录。
- 查询侧按时间线、来源、结果建立低基数索引，并支持 cursor 分页，避免未来审计列表只能全量扫描。

### 对用户的意义

- ✓ 用户执行 Chrome/Computer 权限修复后，记录不再只依赖当前浏览器 `localStorage`，本地 server 也能保留可查询审计日志。
- ✓ 用户刷新页面或重开客户端后，后续可以从 server 审计日志恢复权限动作记录，降低关键安全记录丢失风险。
- ✓ 管理员和团队版后续可以基于同一条本地日志链路扩展检索、导出和 SaaS 聚合，而不是重新设计一套审计数据格式。
- ✓ 当前阶段仍只做本地落盘，不上传 SaaS，不引入真实模型密钥或 prompt 内容，用户隐私边界保持清晰。

## 阶段 23：自动化权限审计服务端查询回填 UI

### 阶段目标

### 阶段作用

- 把阶段 22 的 server list RPC 从“可调用接口”推进为“用户能看到的审计来源”，完成写入到回填的最小闭环。

- 审计区新增来源状态：服务端审计日志、本地浏览器记录、或正在连接服务端，让用户知道当前看到的数据来自哪里。

### 对用户的意义

- ✓ 用户重开插件页后，可以从本地 server 审计日志恢复权限动作记录，不再只依赖当前页面内存或浏览器缓存。
